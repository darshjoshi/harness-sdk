Keep an agent's state and conversation history across restarts and requests. A session persists what the agent knows, so it can pick up where it left off even when your application restarts or runs across several machines.

## What a session contains

A session holds the stateful information agents and multi-agent systems need to function, including:

**Single Agent Sessions**:

- Conversation history (messages)
- Agent state (key-value storage)
- Other stateful information (like [Conversation Manager](./state.md#conversation-manager))

**Multi-Agent Sessions**:

- Orchestrator state and configuration
- Individual agent states and result within the orchestrator
- Cross-agent shared state and context
- Execution flow and node transition history

Built-in session persistence captures and restores this information automatically, so an agent continues a conversation where it left off.

Beyond the built-in options, [third-party session managers](#third-party-session-managers) provide additional storage and memory capabilities.

## Basic usage

### Single agent sessions

Create an agent with a session manager and use it:

<Tabs>
<Tab label="Python">

```python
from strands import Agent
from strands.session import SnapshotSessionManager
from strands.storage import LocalFileStorage

# Create a snapshot session manager with a unique session ID
session_manager = SnapshotSessionManager(
    session_id="test-session",
    storage=LocalFileStorage("./sessions/"),
)

# Create an agent with the session manager
agent = Agent(session_manager=session_manager)

# Use the agent - all messages and state are automatically persisted
agent("Hello!")  # This conversation is persisted
```

### Multi-agent sessions

Multi-agent systems (Graph/Swarm) can also use session management to persist their state.

<Tabs>
<Tab label="Python">

:::caution
Only the orchestrator should have a session manager. Agents inside a graph or swarm must not have their own session manager — Python raises a `ValueError` if you add an agent that has one to a Graph or Swarm.
:::

Pass an explicit storage backend to
[`SnapshotSessionManager`](@api/python/strands.session.snapshot_session_manager):

```python
from strands import Agent
from strands.multiagent import GraphBuilder
from strands.session import SnapshotSessionManager
from strands.storage import LocalFileStorage

researcher = Agent(name="researcher")
writer = Agent(name="writer")

session_manager = SnapshotSessionManager(
    session_id="multi-agent-session",
    storage=LocalFileStorage("./sessions/"),
    multi_agent_save_latest_on="node",
)

builder = GraphBuilder()
builder.add_node(researcher, "researcher")
builder.add_node(writer, "writer")
builder.add_edge("researcher", "writer")
builder.set_session_manager(session_manager)
graph = builder.build()

result = graph("Research and write about AI")
```

The default `"node"` strategy saves after every node and when the invocation ends. Use
`"invocation"` to reduce storage writes and save only when the invocation ends. See the
[API reference](@api/python/strands.session.snapshot_session_manager) for
`MultiAgentSaveLatestStrategy` and its accepted values.

:::caution
Agents inside a multi-agent system must not have their own session manager: only the orchestrator should have one. The orchestrator captures and restores each agent node's state on every execution, so an agent-level session manager would conflict with the orchestrator's persistence.

## Reading the session ID

An agent exposes its session identifier through a readable <Syntax py="agent.session_id" ts="agent.sessionId" /> property. When a session manager is attached, the property returns the manager's <Syntax py="session_id" ts="sessionId" /> (also readable directly on the session manager). Without a session manager, it returns a random 8-character hex string generated at construction, unique per agent instance but not persisted across restarts.

Snapshot-based session managers accept any [Storage](../storage.mdx) backend, including
`InMemoryStorage`, `LocalFileStorage`, `S3Storage`, and custom implementations. See
[Storage](../storage.mdx) for backend configuration, tradeoffs, custom backends, and
required S3 permissions.

<Tabs>
<Tab label="Python">

```python
from strands import Agent
from strands.session import SnapshotSessionManager
from strands.storage import LocalFileStorage

session_manager = SnapshotSessionManager(
    session_id="user-123",
    storage=LocalFileStorage("./sessions/"),
)
agent = Agent(session_manager=session_manager)

print(agent.session_id)            # "user-123"
print(session_manager.session_id)  # "user-123"

# Without a session manager, the id is a generated, non-persisted handle
print(Agent().session_id)          # e.g. "a1b2c3d4"
```

</Tab>
<Tab label="TypeScript">

```typescript
const session = new SessionManager({
  sessionId: 'user-123',
  storage: new LocalFileStorage('./sessions/'),
})
const agent = new Agent({ sessionManager: session })

console.log(agent.sessionId) // "user-123"
console.log(session.sessionId) // "user-123"

// Without a session manager, the id is a generated, non-persisted handle
console.log(new Agent().sessionId) // e.g. "a1b2c3d4"
```

</Tab>
</Tabs>

## Storage backends

[Storage](../storage.mdx) is the single place persistence backends are documented. How session management reaches a backend depends on the manager:

- **`SnapshotSessionManager` (Python) and `SessionManager` (TypeScript)** compose the shared `Storage` abstraction: you pass any `Storage` backend and the manager persists snapshots through it. Manager-level storage takes precedence over an agent-level `storage`. If neither provides storage, Python falls back to `LocalFileStorage("./.strands/")` and TypeScript fails during initialization.
- **`FileSessionManager` and `S3SessionManager` (Python, compatibility path)** configure storage directly with a storage directory or an S3 bucket. They do not take a `Storage` backend.

The examples below show each form.

<Tabs>
<Tab label="Python">

The recommended `SnapshotSessionManager` accepts any [Storage](../storage.mdx) backend, so you choose durability the same way the offloader and memory subsystems do:

```python
from strands import Agent
from strands.session import SnapshotSessionManager
from strands.storage import LocalFileStorage, S3Storage

# File-based persistence (development, single-machine)
session_manager = SnapshotSessionManager(
    session_id="user-123",
    storage=LocalFileStorage("./sessions/"),
)

# S3-based persistence (production, distributed)
session_manager = SnapshotSessionManager(
    session_id="user-123",
    storage=S3Storage(bucket="my-agent-sessions", prefix="production/"),
)

agent = Agent(session_manager=session_manager)
```

The repository-based managers cover Graph, Swarm, and existing repository-format sessions. They configure storage directly rather than through a `Storage` backend:

| Session Manager | Persistence | Best for |
|-----------------|-------------|----------|
| [`FileSessionManager`](@api/python/strands.session.file_session_manager#FileSessionManager) | Local disk | Development, single-machine |
| [`S3SessionManager`](@api/python/strands.session.s3_session_manager#S3SessionManager) | Amazon S3 | Production, distributed |

```python
    session_id="user-123",
    bucket="my-agent-sessions",

```

## How session management works

### Snapshot-based session managers

`SnapshotSessionManager` in Python and `SessionManager` in TypeScript persist a complete
point-in-time snapshot. For single agents, both restore `snapshot_latest` during
initialization and support immutable checkpoints. For graph and swarm, both restore the
latest orchestrator snapshot before the first invocation.

**Single Agent Events**

<Tabs>
<Tab label="Python">

- **Agent Initialization**: When an agent is created with a session manager, it automatically restores any existing state and messages from the session.
- **Message Addition**: When a new message is added to the conversation, it's automatically persisted to the session (`SnapshotSessionManager` does this under `save_latest_on="message"`).
- **Agent Invocation**: After each agent invocation, the agent state is synchronized with the session to capture any updates (`SnapshotSessionManager` default, `save_latest_on="invocation"`).
- **Message Redaction**: When sensitive information needs to be redacted, the session manager replaces the original message with a redacted version while maintaining conversation flow. `SnapshotSessionManager` flushes the redacted content to the latest snapshot under every strategy.
- **Snapshot Trigger** (`SnapshotSessionManager`): Creates an immutable checkpoint when the `snapshot_trigger` callback returns `True`.

</Tab>
<Tab label="TypeScript">

- **Agent Initialization**: Restores state from `snapshot_latest` if it exists.
- **Message Addition** (`saveLatestOn: 'message'`): Saves after each message and
  again when the invocation ends.
- **Agent Invocation** (`saveLatestOn: 'invocation'`, default): Saves when the invocation
  ends.
- **Snapshot Trigger**: Creates an immutable checkpoint when `snapshotTrigger` returns
  `true`.
- **Message Redaction**: Saves redacted content for the `message` and `invocation`
  strategies, but not for `trigger`.

See [Basic Usage](#basic-usage) for configuration examples.

</Tab>
</Tabs>

**Multi-Agent Events**

<Tabs>
<Tab label="Python">

- **Before Multi-Agent Invocation**: Restores orchestrator state from `snapshot_latest` on
  the first invocation.
- **After Node Call** (`multi_agent_save_latest_on="node"`, default): Saves after each
  node and again when the invocation ends.
- **After Multi-Agent Invocation** (`multi_agent_save_latest_on="invocation"`): Saves only
  when the full invocation ends.

</Tab>
<Tab label="TypeScript">

- **Before Multi-Agent Invocation**: Restores orchestrator state from `snapshot_latest` on
  the first invocation.
- **After Node Call** (`multiAgentSaveLatestOn: 'node'`, default): Saves after each node

- **After Multi-Agent Invocation** (`multiAgentSaveLatestOn: 'invocation'`): Saves only

## Immutable snapshots

A [snapshot](./snapshots.mdx) captures agent state at a point in time. Snapshot-based session managers persist them for you: alongside `snapshot_latest`, `SnapshotSessionManager` (Python) and `SessionManager` (TypeScript) keep **immutable snapshots**, append-only checkpoints identified by UUID v7. These enable time-travel restore: you can restore the agent to any prior checkpoint, not just the latest state.

### Creating immutable snapshots

Use the snapshot-trigger callback to control when an immutable snapshot is created. The callback receives the current agent data and returns a boolean:

<Tabs>
<Tab label="Python">

```python
from strands import Agent
from strands.session import SnapshotSessionManager
from strands.storage import LocalFileStorage

session_manager = SnapshotSessionManager(
    session_id="my-session",
    storage=LocalFileStorage("./sessions/"),
    snapshot_trigger=lambda *, agent_data, **_: len(agent_data.messages) % 4 == 0,
)

agent = Agent(session_manager=session_manager)
```

### Listing and restoring snapshots

Snapshot IDs are UUID v7, so they sort lexicographically in chronological order. Use <Syntax py="list_snapshot_ids" ts="listSnapshotIds" /> on the session manager to retrieve them, then pass a <Syntax py="snapshot_id" ts="snapshotId" /> to <Syntax py="restore_snapshot" ts="restoreSnapshot" />:

<Tabs>
<Tab label="Python">

```python
import asyncio

from strands import Agent
from strands.session import SnapshotSessionManager
from strands.storage import LocalFileStorage

session_manager = SnapshotSessionManager(
    session_id="my-session",
    storage=LocalFileStorage("./sessions/"),
)
agent = Agent(session_manager=session_manager)


async def restore() -> None:
    # Force an immutable checkpoint and read it back later
    snapshot_id = await session_manager.save_snapshot(agent, is_latest=False)
    snapshot_ids = await session_manager.list_snapshot_ids(agent)
    assert snapshot_id in snapshot_ids
    await session_manager.restore_snapshot(agent, snapshot_id=snapshot_id)


asyncio.run(restore())
```

## Data models

<Tabs>
<Tab label="Python">

`SnapshotSessionManager` stores a single versioned [`Snapshot`](./snapshots.mdx) JSON blob whose `data` field carries the messages, agent state, conversation manager state, interrupt state, model state, and system prompt.

The record-based models below apply to `FileSessionManager`, `S3SessionManager`, and `RepositorySessionManager`, which persist each message individually:

**Session**

The [`Session`](@api/python/strands.types.session#Session) model is the top-level container for session data:

- **Purpose**: Provides a namespace for organizing multiple agents and their interactions
- **Key Fields**:
  - `session_id`: Unique identifier for the session
  - `session_type`: Type of session (currently `"AGENT"` for both agent & multiagent in order to keep backward compatibility)
  - `created_at`: ISO format timestamp of when the session was created
  - `updated_at`: ISO format timestamp of when the session was last updated

**SessionAgent**

The [`SessionAgent`](@api/python/strands.types.session#SessionAgent) model stores agent-specific data:

- **Purpose**: Maintains the state and configuration of a specific agent within a session
- **Key Fields**:
  - `agent_id`: Unique identifier for the agent within the session
  - `state`: Dictionary containing the agent's state data (key-value pairs)
  - `conversation_manager_state`: Dictionary containing the state of the conversation manager
  - `created_at`: ISO format timestamp of when the agent was created
  - `updated_at`: ISO format timestamp of when the agent was last updated

**SessionMessage**

The [`SessionMessage`](@api/python/strands.types.session#SessionMessage) model stores individual messages in the conversation:

- **Purpose**: Preserves the conversation history with support for message redaction
- **Key Fields**:
  - `message`: The original message content (role, content blocks)
  - `redact_message`: Optional redacted version of the message (used when sensitive information is detected)
  - `message_id`: Index of the message in the agent's messages array
  - `created_at`: ISO format timestamp of when the message was created
  - `updated_at`: ISO format timestamp of when the message was last updated

These data models work together to provide a complete representation of an agent's state and conversation history. The session management system handles serialization and deserialization of these models, including special handling for binary data using base64 encoding.

**Multi-Agent State**

Multi-agent systems serialize their state as JSON objects containing:

- **Orchestrator Configuration**: Settings, parameters, and execution preferences
- **Node State**: Current execution state and node transition history
- **Shared Context**: Cross-agent shared state and variables

</Tab>
<Tab label="TypeScript">

The TypeScript SDK stores session state as a `Snapshot` object written to JSON. Each snapshot contains:

- `data.messages`: The full conversation history
- `data.state`: Agent key-value state
- `data.systemPrompt`: The agent's system prompt
- `schemaVersion`: Schema version for forward compatibility
- `createdAt`: ISO 8601 timestamp

There are two kinds of snapshots:

- **`snapshot_latest.json`**: A single mutable file overwritten on each save. Used to resume the most recent state after a restart.
- **Immutable snapshots** (`immutable_history/snapshot_<uuid7>.json`): Append-only checkpoints created when `snapshotTrigger` fires. Used for time-travel restore.

</Tab>
</Tabs>

To customize a repository-based session, implement the `SessionRepository` interface:

```python
from typing import Optional
from strands import Agent
from strands.session.repository_session_manager import RepositorySessionManager
from strands.session.session_repository import SessionRepository
from strands.types.session import Session, SessionAgent, SessionMessage

class CustomSessionRepository(SessionRepository):
    """Custom session repository implementation."""

    def __init__(self):
        """Initialize with your custom storage backend."""
        # Initialize your storage backend (e.g., database connection)
        self.db = YourDatabaseClient()

    def create_session(self, session: Session) -> Session:
        """Create a new session."""
        self.db.sessions.insert(asdict(session))
        return session

    def read_session(self, session_id: str) -> Optional[Session]:
        """Read a session by ID."""
        data = self.db.sessions.find_one({"session_id": session_id})
        if data:
            return Session.from_dict(data)
        return None

    # Implement other required methods...
    # create_agent, read_agent, update_agent
    # create_message, read_message, update_message, list_messages

# Use your custom repository with RepositorySessionManager
custom_repo = CustomSessionRepository()

    session_id="user-789",
    session_repository=custom_repo
```

Using the same session ID and storage location does not migrate repository-based Python

manager pointed at an existing repository-format session simply finds no snapshot and
starts empty. Existing sessions can continue using their current manager, or you can
migrate them explicitly — see [Migrating from the message-log session managers](#migrating-from-the-message-log-session-managers).

## Migrating from the message-log session managers

:::note[Python only]
This applies to the Python message-log managers (`FileSessionManager`, `S3SessionManager`,
`RepositorySessionManager`). TypeScript has a single `SessionManager` and no equivalent
migration.
:::

`SnapshotSessionManager` is the recommended manager for new single-agent sessions, and it
also covers Graph, Swarm, and `BidiAgent`. If you already have production sessions on a
message-log manager, this section explains **what switching does to existing session data**
and gives a **reference procedure you adapt to your own application** to move those sessions
to snapshots without starting the conversations over.

There is deliberately no built-in, one-call migration command. Every deployment constructs
its agents differently — a custom conversation manager, a specific system prompt, several
agents namespaced under one session, orchestrators with their own topology — and a correct
migration has to reproduce *that* configuration. The SDK cannot guess it for you, so
migration is a short script **you** own, built from the pattern below.

### What swapping the constructor does — and doesn't — carry over

Switching to `SnapshotSessionManager` is often just a one-line change:

```python
# Before
agent = Agent(agent_id="my-agent", session_manager=FileSessionManager(session_id="user-123"))

# After — a valid switch, but existing history is NOT carried over
agent = Agent(
    agent_id="my-agent",
    session_manager=SnapshotSessionManager("user-123", storage=LocalFileStorage("/data/sessions")),
)
```

For a **new session**, that is all you need. The important thing to understand is what it
does to an **existing** session: it does not carry your old data over. The two managers use
different on-disk formats and different key layouts — the message-log managers persist one
object per message plus a mutable agent record under `session_<id>/`, while
`SnapshotSessionManager` persists the whole agent as a single versioned
[`Snapshot`](./snapshots.mdx) blob under `session/<id>/scopes/agent/<agent_id>/snapshots/`. A
snapshot manager pointed at an existing message-log session — even with the same session ID
and storage location — finds no snapshot at its own key and begins with no history and no
state. Nothing errors; the prior conversation is simply not visible to the new manager (the
old data is untouched on disk, just not read).

So the constructor swap is the right move when you are starting fresh, or when you are fine
leaving the old history behind. If instead you need those existing conversations to continue
on snapshots, migrate them first with the procedure below. If you have taken Strands to
production on a message-log manager, your users' sessions live in that format, and migrating
is what lets them carry forward rather than restart.

A second, subtler reason you cannot convert the files directly: **the message log cannot be
faithfully reconstructed by reading files alone.** Compaction (a trimming or summarizing
conversation manager), custom managers, redactions, and orchestrator execution state are
reconstructed by the SDK's *restore* logic, not stored verbatim in a way a naive file copy
would preserve. A correct migration therefore has to run the data back through a live agent
built with the same configuration — which is exactly what the reference procedure does.

### What to pay close attention to when porting a session

A session is far more than its list of messages. Whatever script you write, make sure it
carries every piece of state the legacy restore path rebuilds — these are the things that go
wrong quietly if you miss them:

- **Reconstruct through the real production configuration.** The migrating agent must be
  built with the **same conversation manager, system prompt, model, tools, and identifiers**
  the application uses. Restore is configuration-dependent: a `SummarizingConversationManager`
  reconstructs different state than a sliding-window one. A migration run with a default
  config can produce a snapshot that does not match how the app actually resumes.
- **Match the identifiers exactly.** The `session_id` **and** `agent_id` must be identical on
  both sides. A session can namespace several agents by `agent_id`; each is a separate
  conversation and must be migrated separately under its own id. A mismatched `agent_id`
  migrates into the wrong slot or produces an empty one.
- **Conversation-manager state, including `removed_message_count`.** A trimming or
  summarizing manager tracks how many messages it has dropped. If this offset is lost, the
  migrated session re-reads already-dropped messages or resumes at the wrong point.
- **Redacted message variants.** The legacy format keeps both the original message and its
  `redact_message`. The migration must carry the *applied* (redacted) content so sensitive
  data that was redacted does not reappear.
- **Model state and system prompt.** Both are part of a faithful restore; a stateful model's
  server-side history interacts with restore (see the stateful-model note under
  [How session management works](#how-session-management-works)).
- **Broken tool-use pairs.** A legacy history can contain an orphaned `toolUse` with no
  matching `toolResult`, or a stale/mismatched pair. The message-log restore repairs this
  automatically; your migrated session must be repaired too, or the first invocation can be
  rejected by the model provider. The reference procedure gets this for free by restoring
  through the legacy manager.
- **Never mutate the source.** Only ever read the legacy session. Leaving it intact is what
  lets you verify the migration and roll back if the snapshot does not match.
- **Decide what happens on an already-migrated session.** If the target already holds a
  snapshot, the safe default is to **stop rather than overwrite** (treat a non-empty target
  as "already done" and skip, or raise). Re-running should never clobber a good snapshot.

### Reference procedure: load through the legacy manager, then snapshot

The most reliable migration reuses the SDK's own restore and capture paths instead of
hand-reshaping JSON. You attach the **legacy** manager to a throwaway agent so the SDK
performs its normal restore (state, conversation-manager offset, redactions, and the
broken-tool-use repair), then hand that fully-rehydrated agent to the **snapshot** manager
and force one snapshot. Adapt the identifiers, storage, conversation manager, and system
prompt to match your application:

<Tabs>
<Tab label="Python">

```python
import asyncio

from strands import Agent
from strands.session import FileSessionManager, SnapshotSessionManager
from strands.storage import LocalFileStorage


async def migrate_session(session_id: str, *, agent_id: str = "default") -> None:
    """Copy one message-log session into snapshot format. Non-destructive; stops if already migrated.

    Build `legacy` and `snapshot` to match your application's real configuration — same
    conversation manager, system prompt, model, and tools — so restore reconstructs the
    session the way the app actually resumes it.
    """
    snapshot = SnapshotSessionManager(
        session_id=session_id,
        storage=LocalFileStorage("./snapshot-sessions"),
    )

    # 1. Stop if the target already has a snapshot, so a re-run never clobbers a good one.
    #    restore_snapshot returns True when snapshot_latest exists; probe with a throwaway agent.
    if await snapshot.restore_snapshot(Agent(agent_id=agent_id)):
        raise RuntimeError(f"session={session_id!r} agent={agent_id!r} already migrated")

    # 2. Restore the agent from the legacy message-log session. Constructing the Agent with
    #    the legacy manager runs the full restore: agent state, conversation-manager state
    #    (including removed_message_count), redacted message variants, and the
    #    broken-tool-use repair. Pass the same conversation_manager / system_prompt the app uses.
    legacy = FileSessionManager(session_id=session_id, storage_dir="./legacy-sessions")
    agent = Agent(agent_id=agent_id, session_manager=legacy)

    if not agent.messages and not agent.state.get():
        # Nothing restored — wrong session_id/agent_id, or an empty session.
        raise ValueError(f"no legacy data found for session={session_id!r} agent={agent_id!r}")

    # 3. Capture that rehydrated agent into the snapshot store. Writing snapshot_latest is
    #    what a snapshot manager restores on init, so this is sufficient to resume.
    await snapshot.save_snapshot(agent, is_latest=True)


asyncio.run(migrate_session("user-123"))
```

</Tab>
</Tabs>

A few properties worth calling out:

- **Non-destructive.** It only reads the legacy session and writes a new snapshot; the
  original message-log data is left intact so you can verify the migration before deleting
  it.
- **Stops on an already-migrated target.** The example raises if `snapshot_latest` already
  exists, so re-running never clobbers a good snapshot. (Throwing on a non-empty target is
  the recommended default; skip-and-continue is a reasonable alternative for bulk runs.)
- **Point the two managers at the correct storage.** Use `storage_dir` /
  `bucket` + `prefix` for the legacy manager and the matching `Storage` backend
  (`LocalFileStorage`, `S3Storage`, ...) for the snapshot manager. For an `S3SessionManager`
  source, construct it with its `bucket`/`prefix` instead of `FileSessionManager`.
- **Match the `agent_id`.** A session can namespace several agents by `agent_id`; migrate
  each one, using the same `agent_id` on both sides.

### Where to run the migration

Run it **offline — outside your normal request path**, as a standalone script or one-off
job, not inside a live request handler. It needs read access to the legacy store and write
access to the snapshot store, and it should not be racing a live agent writing the same
session. For a service on AgentCore Runtime (or any hosted runtime), that means a separate
maintenance task/job with access to the same storage backends, **not** a code path inside
your request-serving instance. Treat it like a one-time data backfill.

### Finding the sessions to migrate

The SDK does not enumerate existing sessions for you — **you are responsible for discovering
the session IDs to migrate**, from your own records or from the storage layout:

- **`FileSessionManager`:** the layout is one `session_<id>/` directory per session under
  the storage directory, so listing that directory yields your session IDs.
- **`S3SessionManager`:** list the common prefixes under your `bucket`/`prefix`; each
  `session_<id>/` prefix is one session.
- Within each session, enumerate the `agent_<agent_id>/` entries to find every `agent_id`
  to migrate.

If your application already tracks its own session IDs (for example in your own database),
prefer that list — it is authoritative and avoids coupling your migration to the storage
layout.

### Verify, then cut over

1. **Dry-run on a copy.** Run the migration against a copy of your session store first.
2. **Compare restored state.** Attach a `SnapshotSessionManager` to a fresh agent with the
   same `session_id`/`agent_id` and confirm `agent.messages`, `agent.state.get()`, and the
   conversation-manager state match the legacy session.
3. **Cut over** application code to construct `SnapshotSessionManager` for that session.
4. **Clean up** the legacy data only after you have verified the snapshot restores
   correctly.

### Migrating many sessions

The procedure above migrates one session. To migrate a store, enumerate your session IDs as
described in [Finding the sessions to migrate](#finding-the-sessions-to-migrate) and call
`migrate_session` for each, migrating every `agent_id` within a session. Keep each call
independent and the run idempotent so you can resume after an interruption, and do not
delete any legacy session until its snapshot has been verified.

### Multi-agent and BidiAgent sessions

Multi-agent (Graph/Swarm) orchestrator state and `BidiAgent` sessions are also supported by
`SnapshotSessionManager`, but they do not use the single-agent capture shown above:
orchestrator snapshots are written through lifecycle hooks (after each node or invocation),
and a `BidiAgent` is captured when it stops. Migrating those faithfully means restoring the
whole orchestrator (or stopped Bidi agent) through its legacy manager — as **one unit**, so
topology, shared context, and resume position are preserved — and re-capturing it through
the snapshot manager via the same object. If you run Bidi on a message-log manager today,
treat moving to snapshots as the recommended path and avoid starting new Bidi sessions on
the legacy managers.

## Sessions, agents, and concurrency

Session management is designed around a single live writer per conversation: the session ID plus the agent ID (<Syntax py="agent_id" ts="id" />), or the orchestrator ID for a Graph or Swarm, address one conversation thread in storage.

### One conversation per session

Give each conversation its own session ID. Several agents can share one session ID as long as their agent IDs differ: the session acts as a namespace, and each agent keeps its own messages and state inside it. A single agent instance processes one invocation at a time by default and rejects overlap, as described in [Concurrent Invocations](./agent-loop.md#concurrent-invocations).

### Create an agent per conversation

Constructing an agent is cheap: it wires up tools, hooks, and plugins locally and makes no model call. Build one per request, invoke it, and let it go out of scope. The model provider is the part worth reusing: providers such as `BedrockModel` build their client in the constructor, so create the provider once per process and pass the same instance to every agent.

### Common failure modes

The built-in session managers take no distributed lock, and the single-instance invocation guard is in-process, so neither can detect a second writer running elsewhere. Two patterns result:

- **Two live agents addressing the same session ID and agent ID.** The default IDs (<Syntax py='agent_id="default"' ts="id: 'agent'" />) make this easy to do by accident, including across separate executions that each build their own agent. Overlapping invocations overwrite each other's turns, sequential ones merge two conversations into one history, and neither call errors.
- **Two callers creating the same session at the same time.** Session creation is a check followed by a write, not an atomic operation, so simultaneous cold starts on a new session ID can both succeed, with the later write winning.

## Session persistence best practices

When implementing session persistence in your applications, consider these best practices:

- **Use Unique Session IDs**: Generate unique session IDs for each user or conversation context to prevent data overlap.
- **Session Cleanup**: Implement a strategy for cleaning up old or inactive sessions. Consider adding TTL (Time To Live) for sessions in production environments.
- **Understand Persistence Triggers**: Remember that changes to agent state or messages are only persisted during specific lifecycle events.
- **Concurrent Access**: Session managers are not thread-safe and take no distributed lock. See [Sessions, Agents, and Concurrency](#sessions-agents-and-concurrency).
- **Secure Storage Directories**: The session storage directory is a trusted data store. Restrict filesystem permissions so that only the agent process can read and write to it. In shared or multi-tenant environments (shared volumes, containers), be aware that the SDK does not block symlinks in the session storage directory. If an attacker with write access to the storage directory creates a symlink (e.g., `message_0.json` pointing to an arbitrary file), the SDK will follow it, which could cause sensitive file contents to be loaded into the agent's conversation history.
